## Identity and schema

`articles.url` remains the NOT NULL UNIQUE identity. `track_states` indexes recent
rows by URL; `find_absent_article_urls` matches URLs and suppresses reconciliation
for incomplete/failed sources; upsert still uses `on_conflict='url'`. Original
hash, category, keyword and merged-state comparisons determine UPDATE. Recovery,
run result, source health and collector_runs still consume primary save counts.
Metadata counts never feed those decisions. Frontend medical-press deduplication
and React article keys remain URL-based. Related links keep their own identity;
they are not repurposed to store an article's display URL.

Migration: `supabase/migrations/20261012040738_article_source_detail_url.sql`.
It adds `source_detail_url text` with IF NOT EXISTS, following the root repository's
existing additive keyword-boundary migration. It has no DEFAULT, NOT NULL, UNIQUE,
index, data update, permission or RLS change. Filename was generated by Supabase
CLI 2.120.0 `migration new`, with CLI state under a temporary SUPABASE_HOME;
no migration, reset, push or database command was run. The initial CLI default
home was read-only; selecting its supported state directory resolved generation.

Read-only production inspection found 13 existing article columns, no
source_detail_url, primary key id and UNIQUE url. RLS is enabled; the existing
public SELECT policy uses true and no public write policy exists. An additive
column does not change row visibility. Anonymous readers will be able to read
this **public official URL metadata**, not a credential. Server-side existing
writer credentials remain required for writes; no client write is introduced.
No generated Database type exists to regenerate; optional Article/RelatedLink and
SourceArticle representations handle absent/null values. Admin monitoring's
explicit source/count/run selects are unchanged.

## Validation and display

Collector validation has a small generic HTTPS/absolute-host/credential-free layer
and an initial KDCA policy. Only exact lowercase `www.kdca.go.kr`, board 42,
`/bbs/kdca/42/<positive ASCII numeric ID>/artclView.do`, with IDs of 1–18 digits,
no port, query, fragment, control character or backslash is accepted. Source must
be `질병관리청 보도자료`. Identity must either equal the detail or be the existing
KDCA title-search identity with exactly page=1, srchColumn=title and matching
srchWrd. Unknown institutions are not upgraded by an arbitrary safe HTTPS value;
future providers require an explicit reviewed policy. The database column itself
is generic, so no KDCA-only database constraint is added.

Frontend independently enforces source/host/path/raw canonical URL validation.
It resolves a validated optional detail first, then the unchanged PR #70/#71
verified routing, then existing direct/unverified/institution behavior. NULL,
absent and invalid metadata retain the prior resolver result. All three KDCA
legacy mappings (312868/312844/312845) remain; NHIS logic is unchanged. The shared
JSON fixture tests Python/TypeScript agreement. A syntactically valid URL is not
proof of live page availability or title correspondence: the future parser must
establish that correspondence before supplying metadata.

Server and client article reads use existing `select('*')`, not an unconditional
named-column SELECT. Thus old-schema responses simply omit the optional field.
SourceLink's existing new-tab/rel attributes and guidance dialog are unchanged.

## Independent storage contract

Every primary upsert strips source_detail_url, including copied DELETED rows,
without mutating input. After reconciliation, metadata processing uses immutable
copies of read snapshots and successful primary-save representations. It also
runs when no primary lifecycle change was needed.

| Case | Result |
|---|---|
| 1: NULL → valid | Conditional metadata PATCH; no primary lifecycle save required |
| 2: URL A → URL A | No-op |
| 3: URL A → URL B | Preserve A; aggregate conflict diagnostic |
| 4: valid → NULL/missing | Preserve existing value |
| 5: originally DELETED | Excluded, including a baseline content-change recovery |
| 6: unknown identity in metadata phase | Skip; never insert from metadata alone |

Normal new article insertion still follows the primary lifecycle upsert, then a
separate conditional metadata fill using the returned persisted row. This is
intentionally **two operations, not an atomic INSERT of both fields**: it makes
app-first rollout safe. If optional storage fails, the primary article remains
valid with NULL/absent metadata and the existing UI fallback. A later naturally
scheduled run supplying that value may retry; no manual collection is required.
A new source that supplies no field performs no detail query or diagnostic.

The PATCH sets only source_detail_url and matches persisted id, URL, source,
title, content_hash, status and published_date plus source_detail_url IS NULL.
Only NEW/UPDATE rows with a positive persisted ID and matching source/title/hash/
aware publication instant are eligible. Failed/unrepresented primary saves are
blocked. Duplicate identical candidates yield one metadata PATCH; conflicting
candidates for one identity produce review diagnostics, never a guessed value.
All non-NULL existing values are preserved, even malformed ones, for review.

Concurrent metadata/revision changes cause a safe compare-and-set miss. Repeating
a successful fill is idempotent. Missing column/schema-cache errors (PGRST204 or
42703 mentioning this field) stop remaining optional attempts for that run.
Permission/transport/other optional errors produce aggregate failed diagnostics;
they do not change primary counts, source health, recovery or collector_runs.
Logs contain counts only, not URL payloads, headers, keys or error bodies.

Content hashes continue to be generated from original content/identity inputs;
source_detail_url is never part of hashing. NULL/A/B metadata vectors have equal
hashes. Actual track/save/sync functions are loaded in tests without importing or
running Collector. A frozen main lifecycle function supplies an independent
baseline for 108 status × old detail × new detail × content change × partial
collection combinations. Empty failed-source and full/partial deletion vectors
are also compared. Current parser code emits no detail field, so this phase adds
no extraction/backfill behavior to naturally collected articles.

## Rollout and rollback

| Scenario | Compatibility |
|---|---|
| App first, column absent | Primary payload omits field; wildcard reads work; optional PATCH reports unavailable |
| DB first, old app | Nullable additive field ignored; existing inserts/updates/SELECT and RLS unchanged |
| New DB + new app | Optional conditional metadata fill and validated display enabled |

Recommended expand-first rollout, as a **separate approved operation**:

1. Review infrastructure PR and additive SQL.
2. Approve and apply only this migration using the repository's controlled process.
   Inspect migration history first: this is not authorization to apply all pending migrations.
3. Verify nullable type, existing identities/row counts/RLS and PostgREST schema
   cache readiness; no backfill.
4. Merge/deploy infrastructure after review. This task does not merge or deploy.
5. Create a separate KDCA parser PR for reliable ID/title extraction.
6. Observe natural scheduled collection; never manually dispatch to verify.

Although app-first degrades safely, DB-first is preferred to avoid optional write
failures and expose infrastructure only when its schema is ready. Roll back an
application problem by reverting this PR/application first; retain the nullable
column. Old code ignores it. Do not DROP COLUMN or erase metadata without separate
approval. Incorrect non-NULL metadata correction/backfill is a separately reviewed
operation; this code does not auto-overwrite it.
