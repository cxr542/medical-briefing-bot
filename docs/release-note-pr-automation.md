# Release note PR automation

The generator executes trusted `main` code after a labeled source PR merges. It
creates `automation/release-note/pr-N` and an ordinary note PR; it never updates
main, enables auto-merge, labels the note PR `release-note`, or bypasses rules.
Only Contents write and Pull requests write are requested. No new secrets are
needed. PR CI has Contents read and no production credentials.

The repository owner confirmed Actions PR creation is enabled and default token
permissions are read-only. A GITHUB_TOKEN-created PR can require a write-access
user to approve eligible workflows. Verify the actual head SHA and checks before
merging; neither a missing run nor an old/main run counts as successful PR CI.
The automation does not approve workflows or PRs for its own changes.

## Data contract

Guard and generator share `release-note-contract.mjs`. HTML comments are ignored.
New notes require one supported Category (기능, 개선, 버그 수정, 운영) and Title.
Historical categories, IDs, dates, links, order, and manual edits are preserved.
The UTC merged_at date remains the ID/date source; this is not a KST date change.
A source ID already in main is a no-op even if its PR body was subsequently edited.
Generated notes are prepended. An automation PR must add exactly one note, match
its merged source PR's repository/number/date/link, and change only the generated
JSON. It may refine the new note's text, but cannot modify existing entries.

## Retry and reconciliation

A retry validates and reuses an existing branch without resetting, rebasing,
force-pushing, or regenerating manually amended content. A failed PR creation
leaves the branch available. Closed PRs, unexpected files, or main/branch movement
stop for operator review rather than overwriting data. This deliberately favors
preservation over unattended conflict resolution. Resolve conflicts in a reviewed
PR and let the preservation/source CI validate the final candidate.

After this implementation merges, record its UTC cutover timestamp. The release
note workflow's dedicated manual inputs accept **either** one source PR number
**or** a UTC `since` timestamp. Dry-run defaults to true. Reconciliation paginates
closed PRs, selects merged main PRs with the release-note label since that bound,
and reports existing/missing/review-needed records. Inspect a dry-run first; any
write-enabled retry/reconciliation requires operator authorization. Current PR
metadata is used; historical label removal or body edits require operator review.
It never executes Collector or Recovery. There is no recovery schedule added.

Concurrency serializes writers but is not treated as a durable event queue.
Reconciliation detects eligible missed events. PRs generated by this workflow
are excluded by their branch prefix even if mislabeled, and use No Release Note.

## CI and release gate

`release-note-data` runs on every PR: shared-contract and mock API tests, committed
JSON validation, and automation-PR diff/preservation/source checks. The frontend
workflow also runs for generated JSON, parser/generator, and related test changes,
including full npm test and production build. Native Collector smoke remains
conditionally scoped in its existing workflow. CI uses synthetic/local fixtures.

Branch push/PR creation may cause Vercel Preview builds independently of Actions
event suppression. Production/Preview credential isolation remains a separate
required operational gate. Note PR merge causes the existing main deployment;
it is not deployment authorization in itself. Source code merge and note merge
remain separate releases. No Collector/Recovery configuration changes are needed.

## Rollout and rollback

This feature is inactive until the implementation PR merges. Do not run the new
workflow manually from an implementation branch. Replace the old workflow in one
merge, validate naturally created note PR CI under approved conditions, then
apply main protection separately. No Actions-wide bypass is needed.

If generation fails, preserve data/branches and pause automation; use reviewed
manual note PRs. After protection is enabled, do not restore main direct push as
a rollback. Reverting the implementation requires review of that unsafe legacy
behavior. Existing notes are never deleted as a recovery measure.
